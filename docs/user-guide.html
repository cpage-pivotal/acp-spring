Spring AI ACP Reference

Spring AI ACP drives any Agent Client Protocol coding agent (Goose, Codex, OpenCode, or any of the agents in the ACP registry) from a Spring Boot application, behind one API and one configuration model.

Spring AI ACP relates to coding agents the way Spring Data relates to databases:

  • application code talks to one abstraction, AgentClient;
  • configuration carries options that work on every agent, plus a per-agent escape hatch;
  • the agent behind it is chosen by one property, spring.acp.runtime.
application.yaml
spring:
  acp:
    runtime: goose        # or codex, opencode, a registry id
    model: gpt-5.6-terra  # a request, not an assignment
String answer = agentClient.prompt()
        .session("review-123")
        .user("Inspect this change")
        .call()
        .content();

The agent itself is a separate process: Spring AI ACP launches it (or attaches to it), speaks ACP to it over stdio or WebSocket, supervises it, and turns what it streams back into typed Java events. Around that conversation, Spring AI ACP configures the things that make an agent yours:

Three tiers of configuration

ACP standardizes the conversation, not the provisioning. So each property belongs to one of three tiers, and the tier tells you how portable it is:

Portablespring.acp.*Honoured by every runtime: workspace, mcp-servers, skills, permissions, timeout, provider credentials.

Getting Started

Prerequisites

  • Java 21 and Spring Boot 4.1.
  • An agent you can run. Spring AI ACP does not package agent binaries. For the compiled adapters:
    • Goose: the goose CLI on the PATH, or GOOSE_CLI_PATH pointing at it. Verified against goose 1.51.
    • Codex: Node.js with npx. The adapter runs npx -y @agentclientprotocol/codex-acp@1.13.1, so the first start downloads it.
    • OpenCode: the opencode CLI on the PATH, or OPENCODE_CLI_PATH. Verified against opencode 1.18.
    • Registry agents: nothing pre-installed; the agent is downloaded and checksum-verified. Agents distributed through npm or PyPI need npx or uvx.
  • Model credentials, either already configured in the agent itself (for example goose configure or codex login) or given to Spring AI ACP through spring.acp.provider (see Models and Providers).

Add the dependency

Releases are published to a public Artifact Registry repository; no credentials are needed to read it. Add the repository and one runtime starter:

<repositories>
    <repository>
        <id>spring-ai-acp</id>
        <url>https://us-central1-maven.pkg.dev/cf-mcp/maven-public</url>
    </repository>
</repositories>

<dependencies>
    <dependency>
        <groupId>org.springaicommunity</groupId>
        <artifactId>spring-ai-acp-boot-starter-goose</artifactId>
        <version>0.3.0</version>
    </dependency>
</dependencies>
repositories {
    mavenCentral()
    maven { url = uri("https://us-central1-maven.pkg.dev/cf-mcp/maven-public") }
}

dependencies {
    implementation("org.springaicommunity:spring-ai-acp-boot-starter-goose:0.3.0")
}

Replace -goose with -codex, -opencode or -registry for another agent. No @Enable… annotation or bean definition is needed.

Configure

src/main/resources/application.yaml
spring:
  acp:
    runtime: goose                  # optional while goose is the only adapter on the classpath
    workspace: ${AGENT_WORKSPACE:./workspace}   # the agent's working directory; must exist
    timeout: 5m                     # longest a single turn may take

The workspace is the agent's working directory (its ACP session cwd). It is also where the agent looks for AGENTS.md and where skills are installed, so most of this guide comes back to it. A relative path is resolved against the JVM's working directory; left unset, the JVM's working directory itself is used. It must be an existing directory.

Send a prompt

@SpringBootApplication
public class ReviewApplication {

    public static void main(String[] args) {
        SpringApplication.run(ReviewApplication.class, args);
    }

    @Bean
    ApplicationRunner demo(AgentClient agent) {
        return args -> System.out.println(
                agent.prompt("Summarize what is in this directory").call().content());
    }
}

AgentClient is a thread-safe singleton. The agent process is started on the first prompt, not at context refresh: an application whose agent is misconfigured still starts, and reports the problem the first time it is used. The process is stopped when the context closes.

Tip

The repository's samples/smoke-app has all three adapters and the registry on its classpath. After mvn install in the Spring AI ACP checkout, run it against each agent in turn:

mvn -pl samples/smoke-app spring-boot:run
mvn -pl samples/smoke-app spring-boot:run -Dspring-boot.run.arguments=--spring.acp.runtime=codex
mvn -pl samples/smoke-app spring-boot:run -Dspring-boot.run.arguments=--spring.acp.runtime=opencode
mvn -pl samples/smoke-app spring-boot:run -Dspring-boot.run.arguments=--spring.acp.runtime=gemini

AgentClient API

Every call starts with prompt() and describes one turn. Nothing is sent until call() or stream().

Blocking and streaming

// Blocking: wait for the finished answer.
AgentClient.AgentResponse response = agent.prompt()
        .session("review-123")                          // a named, reusable conversation
        .user("Inspect the pending change")
        .options(o -> o.timeout(Duration.ofMinutes(10)))
        .call();

String text = response.content();                        // assistant text only
AcpSchema.StopReason why = response.completion().reason();

// Streaming: every event as it happens.
Flux<AgentEvent> events = agent.prompt()
        .session("review-123")
        .user("Now focus on security")
        .stream()
        .events();

// Or just the text, e.g. for a server-sent-events endpoint.
Flux<String> text = agent.prompt("Explain the build").stream().content();
MethodMeaning
session(name)Runs in a named conversation; repeat calls with the same name keep context. Without it the turn runs in a throwaway session closed when the turn ends. Names match [A-Za-z0-9][A-Za-z0-9._-]{0,127}.
user(text)Appends user text; call more than once to build up a prompt. prompt(text) is shorthand.
options(…)Per-turn overrides of timeout, model, mode and provider, as an AgentOptions or a builder lambda.
principal(p)Runs on behalf of a user: their MCP credentials, their session (see per-user OAuth).
call()Blocks and returns the finished turn.
stream()A Flux ending in exactly one terminal event. Cancelling the subscription cancels the turn on the agent.
Note

Workspace, credentials and MCP servers are not per-request options. They are fixed when the agent process starts, so a per-request override would silently do nothing.

Events

AgentEvent is a sealed interface of records, so a switch over it can be exhaustive:

agent.prompt().session("review-123").user("Review the diff").stream().events()
        .doOnNext(event -> {
            switch (event) {
                case AgentEvent.Text t            -> ui.append(t.text());
                case AgentEvent.Thought t         -> log.debug("thinking: {}", t.text());
                case AgentEvent.ToolCallStarted s -> ui.toolStarted(s.id(), s.title(), s.kind());
                case AgentEvent.ToolCallUpdated u -> ui.toolProgress(u.id(), u.status());
                case AgentEvent.PlanUpdated p     -> ui.replacePlan(p.entries());
                case AgentEvent.ConfigChanged c   -> log.info("agent reconfigured: {}", c.options());
                case AgentEvent.ModeChanged m     -> log.info("mode is now {}", m.modeId());
                case AgentEvent.UsageUpdated u    -> meter.context(u.contextUsed(), u.contextSize());
                case AgentEvent.Completed c       -> ui.done(c.reason());
                case AgentEvent.Failed f          -> ui.error(f.cause());
            }
        })
        .blockLast();
EventMeaning
TextAssistant-visible text, as deltas. What content() collects.
ThoughtReasoning the agent chose to surface. Not part of the answer.
ToolCallStartedA tool call began: id, human-readable title, kind.
ToolCallUpdatedProgress or completion of a call, keyed by the same id.
PlanUpdatedThe agent's current plan. Replaces any earlier plan in the turn.
ConfigChanged, ModeChangedThe agent reconfigured itself mid-turn.
UsageUpdatedContext window used of its size, cumulative for the session, with cost when the agent reports one.
Completed (terminal)The turn reached the agent's own stop condition.
Failed (terminal)It did not: error, timeout, lost connection or cancellation.

Every turn emits exactly one terminal event, whatever happens, so a UI can close its progress indicator in one place. event.terminal() tests for either.

Named sessions

agent.prompt().session("pr-482").user("What does this PR change?").call();
agent.prompt().session("pr-482").user("Any security concerns in it?").call();   // remembers the first turn

Idle named sessions are closed after spring.acp.pool.session-ttl (60 minutes by default). Scope names to a unit of work, such as a PR, a ticket or a chat, so context does not grow without bound. Only one turn runs in a session at a time.

openSession(name) opens a session without spending a turn. It is how to learn what the negotiated tier actually achieved before the first prompt:

import org.springaicommunity.acp.runtime.AgentRuntime.PortableOption;

SessionConfiguration config = agent.openSession("review-123").configuration();
config.applied(PortableOption.MODEL);          // Optional: the model this session is really using
config.unsupported();                          // what was asked for and could not be honoured
config.resolutions().values().forEach(r ->     // requested, applied, and by which mechanism
        log.info("{}: {} -> {} ({})", r.option(), r.requested(), r.applied(), r.mechanism()));

Stored conversations

agent.sessions() manages the conversations the agent keeps. Every operation is optional in ACP, and the runtimes implement different subsets, so ask first:

AgentSessions sessions = agent.sessions();
if (sessions.supports(AgentSessions.Operation.LIST)) {
    List<StoredSession> stored = sessions.list();
}
if (sessions.supports(AgentSessions.Operation.LOAD)) {
    sessions.load("review-123", storedId);      // reattach and replay history under this name
}
sessions.close("review-123");                   // always succeeds, told or not

Agent Runtimes

A runtime is an adapter that knows how to launch one agent and what that agent calls its options. Application code never names one; spring.acp.runtime does.

spring.acp.runtimeStarterLaunchesTransport
goosespring-ai-acp-boot-starter-goosegoose acp, or a supervised goose servestdio, or WebSocket
codexspring-ai-acp-boot-starter-codexnpx -y @agentclientprotocol/codex-acp@1.13.1stdio
opencodespring-ai-acp-boot-starter-opencodeopencode acpstdio
any registry id, e.g. geminispring-ai-acp-boot-starter-registrywhatever the ACP registry publishesstdio

How the runtime is selected

  • One adapter on the classpath: spring.acp.runtime may be left out.
  • Several adapters, or only the registry: it must be set. There is no default agent; startup fails with a message listing the choices.
  • A compiled adapter always wins over the registry for the same id, because it knows things the catalogue does not.
  • A spring.acp.runtimes.<id> block for an id nothing can supply fails startup rather than being silently ignored.

Swapping the runtime

There are three ways to move an application from one agent to another. None involves changing Java code.

1. Replace the starter

Swap spring-ai-acp-boot-starter-goose for spring-ai-acp-boot-starter-opencode (say), and change or remove spring.acp.runtime. Best when a deployment only ever uses one agent: the other adapters stay off the classpath.

2. Ship several adapters and choose at run time

Put every starter you want to support on the classpath and pick one with any Spring property source:

# command line
java -jar app.jar --spring.acp.runtime=opencode

# environment variable (relaxed binding)
SPRING_ACP_RUNTIME=codex java -jar app.jar

# a profile that carries the runtime and everything that goes with it
java -jar app.jar --spring.profiles.active=codex

A profile is the right tool when the runtimes need different models or credentials, as in the acp-meridian example:

application.yaml
spring:
  acp:
    runtime: goose
    model: deepseek-ai/DeepSeek-V4-Flash-0731
    provider: { id: openai, api-type: openai, base-url: ${GENAI_API_BASE}, api-key: ${GENAI_API_KEY} }
---
spring:
  config:
    activate:
      on-profile: codex
  acp:
    runtime: codex
    model: gpt-5.6-terra
    provider: { id: openai, api-type: openai, base-url: "", api-key: ${OPENAI_API_KEY} }

3. Let an operator decide with agents.yaml

Import a standalone file whose keys are implicitly under spring.acp. It gets relaxed binding, profiles and ${…} placeholders like any other config file, and validation errors point at its lines:

application.yaml
spring:
  config:
    import: optional:agents.yaml          # or optional:acp:/etc/myapp/agent-config.yaml
agents.yaml (next to the jar)
runtime: opencode
model: gpt-5.4-mini
permissions:
  policy: deny
runtimes:
  opencode:
    config: { share: disabled }

Keys that already start with spring. are left alone, so the file may carry an unrelated property too.

Runtime Configuration

Each agent has settings of its own that ACP does not standardize: Goose's built-in extensions, Codex's sandbox, OpenCode's per-tool permissions. They live in the third configuration tier, one block per runtime:

application.yaml
spring:
  acp:
    runtime: goose
    runtimes:
      goose:    { builtins: developer }                       # used: goose is selected
      codex:    { config-toml: { model_reasoning_effort: high } }   # ignored until codex is selected
      opencode: { config: { share: disabled } }               # ignored until opencode is selected
  • Only the selected runtime reads its block. Blocks for the others are inert, so an application can keep settings for every agent it supports side by side. A block for an id that no adapter or registry can supply fails startup, which catches a misspelled runtime name.
  • Applied last. Whatever the adapter derives from portable properties (provider credentials, a bring-your-own endpoint) is written first, and the tier-3 block is laid over it. env therefore wins over every variable the adapter sets. For the config-file blocks the merge is by top-level key, so a top-level key you set replaces the adapter's value for that key, including a whole table.
  • Any property source works. Top-level keys bind relaxed, while nested keys keep the spelling you wrote, because they end up verbatim in a file the agent parses: 
    spring.acp.runtimes.codex.config-toml.model_reasoning_effort=high
spring.acp.runtimes.goose.env.GOOSE_MAX_TURNS=40
  • Files are written to spring.acp.runtime-home (a directory under the JVM's temp directory by default), never to the workspace.
Tip

Prefer the portable property whenever one exists. It keeps working when you swap agents, and the negotiated ones report what was applied. Use tier 3 for what is genuinely agent-specific.

Goose

The adapter launches goose acp over stdio and sets GOOSE_DISABLE_KEYRING=1 and GOOSE_TELEMETRY_ENABLED=false. Goose still reads its own ~/.config/goose/config.yaml for anything not set here.

application.yaml: every Goose key
spring:
  acp:
    runtimes:
      goose:
        builtins: [ developer, todo, skills ]  # --with-builtin; a comma-separated string works too
        env:                                   # environment for the goose process, applied last
          GOOSE_THINKING_EFFORT: high
          GOOSE_MAX_TURNS: "40"
        serve:                                 # speak ACP over goose's WebSocket server instead of stdio
          transport: websocket                 # stdio (default) | websocket
          host: 127.0.0.1
          port: 0                              # 0 = any free port
          startup-timeout: PT30S
        log-dir: /var/log/goose/logs           # where goose writes its log, if not the default
        mcp:
          answer-discover: true                # workaround for MCP gateways; see below

Built-in extensions

Goose's own tools come from extensions bundled in the binary. builtins enables them by name, each passed as --with-builtin:

NameProvides
developerCode editing and shell access. Needed for the agent to change files or run commands, including a skill's scripts.
computercontrollerWeb scraping, file caching and automation.
memoryTools to save and retrieve durable memories.
autovisualiserData visualisation and UI generation (charts, diagrams).
tutorialInteractive goose tutorials. Rarely useful in an application.
todo, skillsGoose platform extensions: a task list the agent keeps for multi-step work, and support for Agent Skills.

builtins adds to the extensions enabled in goose's own config.yaml. A developer machine usually has several enabled there. A server or container usually has no goose config at all, so name every extension the application relies on. For example, developer and skills if it uses skills with scripts. Otherwise an application that works on your laptop quietly loses its tools in production.

Note

A misspelled name does not stop goose. It writes Failed to load extension <name>: … Unknown extension to its log and carries on. Spring AI ACP reads that log for agents it started, so the mistake appears as a WARN line and in AgentClient.notices(), worded as a server that could not be loaded.

For tools that are not built in, declare an MCP server under spring.acp.mcp-servers rather than a goose extension. It is the same thing to goose, and it stays portable.

Environment variables

Goose reads each of its config.yaml settings from an environment variable of the same name first, so the env block can set any of them. Some that are useful from an application:

VariableEffect

Modes

Running goose as a WebSocket server

With serve.transport: websocket, the adapter starts goose serve on host and port, generates a secret it sends as a header on every connection, and supervises the process: it is health-checked and restarted with backoff, and stopped when the application closes. Use it when you want goose to outlive individual connections, as the goose buildpack did. Stdio stays the default because it is what every other runtime supports. Keep host on loopback unless you mean to expose the server.

Log directory and MCP gateways

  • log-dir tells Spring AI ACP where goose writes its log, which is the only place goose reports an MCP server or extension it could not load. Defaults to $XDG_STATE_HOME/goose/logs, else ~/.local/state/goose/logs. Set it only if your deployment moves goose's state.
  • mcp.answer-discover: true answers goose's server/discover probe on behalf of MCP gateways that reply to it with an error goose cannot correlate. See MCP Servers.

Sandbox and approvals

codex-acp exposes Codex's approval and sandbox settings as three presets of its mode option, and spring.acp.mode selects one:

spring.acp.modecodex-acp nameBehaviour
read-onlyAsk for approvalAlways asks to edit files outside the workspace and to use the internet. Still writes inside the workspace without asking.
agent (default)Approve for meSandboxed; asks only for actions it detects as potentially unsafe.
agent-full-accessFull accessNo sandbox: unrestricted access to the internet and to any file the process can reach. Never asks.
planPlan (collaboration_mode)Plans before changing anything; the mode to pair with permissions.policy: deny for a reviewer.

To run Codex outside its sandbox, select full access:

spring:
  acp:
    runtime: codex
    mode: agent-full-access
    on-unsupported: fail        # refuse to run if the preset cannot be applied

or only for the turns that need it:

agent.prompt().session("migration").user("Run the full integration build")
        .options(o -> o.mode("agent-full-access"))
        .call();
Important

Setting sandbox_mode or approval_policy in config-toml does not change this. Measured against codex-acp 1.13.0: with sandbox_mode = "danger-full-access" and approval_policy = "never" in config.toml, new sessions still start in agent. Use spring.acp.mode. With on-unsupported: fail you will know if it was not applied.

Warning

Under agent-full-access Codex asks nothing, so spring.acp.permissions never gets a request to refuse. Whatever the JVM's user can reach, the agent can change, and the model's credentials are in its environment. Only run it where the machine or container is itself the sandbox: a disposable container with no secrets beyond the ones it needs, and nothing mounted that you would mind losing.

spring.acp.mode takes one value. codex-acp offers both a mode and a collaboration_mode option, and Spring AI ACP applies the value to whichever option offers it.

config.toml

config-toml is written as Codex's config.toml. YAML maps become TOML tables, and lists of scalars become arrays. Keys are Codex's own; see the Codex configuration reference.

spring:
  acp:
    runtimes:
      codex:
        config-toml:
          model_reasoning_effort: high           # low | medium | high | xhigh | max | ultra, as codex-acp advertises
          model_reasoning_summary: concise
          shell_environment_policy:              # becomes the [shell_environment_policy] table
            inherit: core

model_reasoning_effort is the way to set reasoning effort: codex-acp advertises it as a reasoning_effort option with no portable property, and a value in config.toml becomes that option's starting value (verified against 1.13.0).

Caution

The file the adapter writes is the only config.toml Codex reads. Setting config-toml moves CODEX_HOME to a directory the adapter owns, so a developer's ~/.codex/config.toml (their model, MCP servers, profiles) stops applying. That is deliberate, since a server should not depend on a personal file, but it can surprise you locally.

Pinning or pre-installing codex-acp

OpenCode

The adapter launches opencode acp over stdio. OpenCode advertises exactly two options, model and mode, so nearly all of its behaviour is configured through its own opencode.json.

application.yaml: every OpenCode key
spring:
  acp:
    runtimes:
      opencode:
        command: /opt/opencode/bin/opencode   # default: OPENCODE_CLI_PATH, else "opencode" on the PATH
        args: [ --print-logs ]
        config:                               # written as opencode.json, pointed at by OPENCODE_CONFIG
          share: disabled
          autoupdate: false
        config-file: /etc/myapp/opencode.json # where to write it, instead of /opencode.json
        env:
          HTTPS_PROXY: http://proxy.internal:3128

opencode.json

config is written as JSON with OpenCode's own keys; see the OpenCode config reference. OpenCode merges configuration files rather than replacing them, in this order (later wins, key by key):

  1. the global ~/.config/opencode/opencode.json;
  2. the file the adapter writes (OPENCODE_CONFIG);
  3. a project opencode.json in the workspace.

Measured against opencode 1.18.31: a model in the workspace's opencode.json overrode the one in the adapter's file, while the adapter's other keys still applied. Unlike Codex, relocating the config file does not affect OpenCode's login, which lives elsewhere.

Per-tool permissions

OpenCode's permission block sets, per tool, whether it may act (allow), must not (deny), or must ask (ask). An ask reaches your application as an ACP permission request and is answered by spring.acp.permissions. This gives you a review gate in the default build mode, finer than switching to plan:

spring:
  acp:
    runtimes:
      opencode:
        config:
          permission:
            edit: ask                  # every file change asks
            bash:
              "*": ask                 # shell commands ask…
              "git status": allow      # …except these
              "git diff*": allow
            webfetch: deny
            external_directory: deny   # nothing outside the workspace
    permissions:
      policy: deny                     # every ask is refused: the agent reads, and runs only git status/diff

Tools include read, edit, glob, grep, list, bash, task, webfetch, websearch, skill and external_directory. A single value (permission: ask) applies to all of them.

Modes and custom agents

OpenCode's modes are its primary agents: build (the default) and plan. Define your own in config.agent and it becomes a mode that spring.acp.mode can select. Verified against 1.18.31, where a custom review agent appeared as a mode beside build and plan and could be set:

spring:
  acp:
    runtime: opencode
    mode: review                        # select the agent defined below
    runtimes:
      opencode:
        config:
          agent:
            review:
              mode: primary             # primary agents are ACP modes
              description: Reviews changes without editing them
              prompt: You review code for correctness and security. Never edit files.
              permission:
                edit: deny
                bash: ask

default_agent in config sets the mode new sessions start in. Prefer spring.acp.mode, which reports whether it was applied.

Registry agents

With spring-ai-acp-boot-starter-registry, spring.acp.runtime can name any agent in the ACP registry that no compiled adapter claims. The agent is resolved from a cached catalogue snapshot, downloaded, verified against its published SHA-256, unpacked and launched:

spring:
  acp:
    runtime: gemini
    registry:
      require-checksum: true        # default; refuse agents published without a sha256
      cache: ${user.home}/.spring-ai-acp/agents
      refresh: 24h
      offline: false                # true: bundled snapshot and already-installed agents only
    runtimes:
      gemini:
        args: [ --debug ]           # appended to the arguments the registry specifies
        env:
          GEMINI_API_KEY: ${GEMINI_API_KEY}

A registry agent has only two tier-3 keys, args and env, because nothing is known about its config files. It reaches the negotiated tier only through ACP's own option categories and the obvious ids model, mode and provider. Provider credentials reach it as <API_TYPE>_API_KEY and <API_TYPE>_BASE_URL; anything else goes in env.

Warning

A registry agent is an executable downloaded from the internet and run with your application's credentials in its environment. Several binary agents publish no checksum; running one requires spring.acp.registry.require-checksum: false, which you should set only deliberately. Pin the catalogue with a file: URL in spring.acp.registry.url for reproducible builds.

Models and Providers

Selecting a model

spring:
  acp:
    model: gpt-5.6-terra
    on-unsupported: fail       # fail | warn (default) | ignore

spring.acp.model is a request. When a session opens, Spring AI ACP reads the options the agent advertises and matches the request against them, in order: exact id, display name, <provider>/<model>, then a suffix match that must be unique. Only then does it send session/set_config_option. It never sends a value the agent did not advertise, because some agents (goose) accept an unknown model id and fail later, inside the turn.

When nothing matches, on-unsupported decides:

ValueBehaviour
failThrows UnsupportedAgentOptionException when the session opens. Use in production when a wrong model is worse than a failed request.
warnLogs once per option per runtime, naming what the agent does offer, and continues on the agent's default.
ignoreContinues silently.
A warn, naming the alternatives
WARN  Runtime 'goose' cannot honor model='gpt-4o-from-2024' (the agent's 'model' option offers
      gpt-6-astra, gpt-5.6-luna, gpt-5.6-sol, gpt-5.6-terra, … (94 in all));
      continuing with the agent's own default.
Tip

Leave model unset to use whatever the agent is already configured with, which is the one model its credentials are sure to reach. To see what an agent offers, set a deliberately wrong model with warn and read the warning, or inspect agent.openSession("probe").configOptions().

Override per turn with .options(o -> o.model("gpt-5.6-sol")). Options are negotiated once per session, and again only when a turn asks for something different. To see what was applied, read openSession(name).configuration() (above); each option reports a Mechanism: CONFIG_OPTION, ENDPOINT, SESSION_MODE, SESSION_MODEL, PROVIDERS_SET, OUT_OF_BAND, UNSUPPORTED or NOT_REQUESTED.

Provider credentials

An agent either already has credentials (its own login or config file), or you give it one through spring.acp.provider. The provider block is fixed at process start and never per request.

spring:
  acp:
    model: gpt-5.6-terra
    provider:
      id: openai                  # negotiated: the provider as the agent names it
      api-type: openai            # the API dialect; also names the env vars (OPENAI_API_KEY, …)
      api-key: ${OPENAI_API_KEY}  # never logged
      # base-url: …               # only for an endpoint of your own; see below
      # headers: { X-Team: platform }
PropertyMeaning
provider.idWhich provider to use, as the agent names it. Negotiated like model; OpenCode takes it as the model prefix.
provider.api-typeThe wire dialect. Its upper-cased form names the environment variables: openai → OPENAI_API_KEY, OPENAI_BASE_URL; azure_openai → AZURE_OPENAI_API_KEY.
provider.api-keyThe key. Travels in the agent's environment or config file (as an {env:…} reference where the format allows), or through ACP authenticate for Codex.

Bring your own endpoint

Point the agent at a platform gateway, a proxy, or a model server you run, with four properties and no runtime-specific block:

spring:

    runtime: goose
    model: deepseek-ai/DeepSeek-V4-Flash-0731
    provider:
      id: openai
      api-type: openai
      base-url: https://gateway.example.com/team-x/openai   # "/v1" is added when there is no version segment
      api-key: ${GENAI_API_KEY}

With base-url set, the endpoint's own /models listing decides which models exist, not the agent's built-in catalogue, and the model is applied even though the agent never advertised it (Mechanism.ENDPOINT). An endpoint that publishes no listing refuses nothing. This applies to model only; mode and provider.id are still checked against the agent.

MCP Servers

MCP servers give the agent tools. They are the most portable part of the configuration: ACP passes the list to the agent in session/new, so every compliant agent honours it with no adapter involved. Servers are offered to every session the client opens.

Declaring servers

Each server sets either url (HTTP) or command (stdio). Both, or neither, fails at startup.

application.yaml
spring:
  acp:
    mcp-servers:
      # Remote server over streamable HTTP.
      - name: inventory
        url: https://mcp.example.com/inventory/mcp
        headers:
          Authorization: "Bearer ${INVENTORY_TOKEN}"

      # Local server the agent launches as a child process.
      - name: filesystem
        command: npx
        args: [ "-y", "@modelcontextprotocol/server-filesystem", "/srv/agent-workspace" ]
        env:
          LOG_LEVEL: info
FieldTransportNotes
namebothRequired, unique. Tools usually surface prefixed with it.
urlHTTPHTTPS, or HTTP for localhost/loopback and *.apps.internal. No credentials in the URL.
headersHTTPStatic headers such as a service token. Validated; never logged.
authHTTPnone (default) or oauth for per-user sign-in (below).
commandstdioThe executable the agent launches.
argsstdioArguments, in order.
envstdioEnvironment for the server process.

A Spring AI MCP server of your own is just another HTTP entry. At INFO, Spring AI ACP logs the host and path of each server it offers when a session opens, never its headers.

Important

Declaring a server is not permission to call it. If the agent asks permission before calling a tool, the default policy (deny) refuses it. Configuring MCP servers is two steps: declare them here, then grant them in Permissions.

When a server fails to load

An MCP server the agent cannot reach is reported nowhere in ACP: the session opens normally, the model answers, and it simply has no tools. Goose writes the failure only to its own log file, and Spring AI ACP watches that log for agents it started:

spring:
  acp:
    mcp:
      on-server-failure: fail    # warn (default): log it and carry on; fail: refuse the session
      detect-timeout: 2s         # how long session opening waits for a report (fail only)
agent.notices().forEach(n -> log.warn("{} {}: {}", n.severity(), n.subject(), n.detail()));
Note

Only the Goose adapter can report load failures today. On other runtimes these settings are inert and notices() stays empty; the symptom is the model saying it lacks tools its instructions say it has.

Credentials the agent never sees

Static headers are handed to the agent and frozen for the session. For expiring tokens, or tokens that belong to a particular user, contribute an McpCredentialsProvider bean instead:

@Bean
McpCredentialsProvider mcpCredentials(TokenService tokens) {
    return (server, principal) -> server.name().equals("inventory")
            ? Optional.of(McpCredentials.bearer(() -> tokens.currentToken(principal)))   // asked per request
            : Optional.empty();                                                         // as configured
}

Each server the provider answers for is routed through a loopback proxy on 127.0.0.1. The agent is given http://127.0.0.1:<port>/<random-token>/<server>; the proxy adds the headers on every forwarded request (so a token refresh lands between two tool calls) and drops the agent's own Authorization. Each session gets its own unguessable route, released when the session ends. A provider that throws refuses the session before the agent hears of it.

Per-user OAuth

For MCP servers that implement the MCP authorization spec, add spring-ai-acp-mcp-oauth and mark the server auth: oauth. Authorization-server discovery, dynamic client registration, PKCE and the resource parameter are handled for you; each user signs in once per server, and tokens are refreshed as needed.

pom.xml
<dependency>
    <groupId>org.springaicommunity</groupId>
    <artifactId>spring-ai-acp-mcp-oauth</artifactId>
    <version>0.3.0</version>
</dependency>
application.yaml
spring:
  acp:
    mcp-servers:
      - name: finops-mcp
        url: https://gateway.example.com/finops-mcp/mcp
        auth: oauth
    mcp:
      oauth:
        mode: web                  # web (default) | local
        client-name: Capacity Agent
        store: jdbc                # memory (web default) | jdbc | file (local default)

Web applications

Users sign in through Spring Security's redirect. Add the MCP configurer to your filter chain:

@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .oauth2Login(Customizer.withDefaults())
            .with(McpClientOAuth2Configurer.mcpClientOAuth2(), mcp -> mcp.cimd(false))
            .build();
}

The signed-in user becomes the SessionPrincipal of every prompt described on a request thread. A named session belongs to its principal; another user reusing the name gets SessionOwnershipException. On a reactive stack, pass .principal(SessionPrincipal.of(name)) explicitly. To send a user to sign in before a stream starts, call OAuth2McpCredentialsProvider.requireAuthorized(principal) in the controller. With store: jdbc, registrations and tokens are shared across instances (schema: org/springaicommunity/acp/mcp/oauth/acp-mcp-oauth-schema.sql plus Spring Security's oauth2_authorized_client).

Terminal applications

mode: local needs no filter chain. The first run opens a browser for each server (a loopback redirect on 127.0.0.1); the operating-system user is the principal, and sign-ins are kept in ~/.config/<spring.application.name>/acp-mcp-oauth.json (mode 600), so later runs refresh silently.

Goose and MCP gateways

Goose 1.51 opens an HTTP MCP connection with a server/discover probe. Some gateways answer it with an error goose cannot correlate, so goose never falls back to initialize and the server silently never loads. spring.acp.runtimes.goose.mcp.answer-discover: true answers the probe correctly on the gateway's behalf. Enable it only for gateways that need it, and remove it once either side is fixed.

Skills

A skill is a directory holding a SKILL.md: a named, described procedure the agent loads when the task matches its description, optionally with scripts and reference files beside it. Skills are how you teach an agent your procedures (a release checklist, a review rubric, how to send an email) without putting them in every prompt.

ACP says nothing about skills, but Goose, Codex and OpenCode all read them from <workspace>/.agents/skills/<name>/. Spring AI ACP installs the skills you configure into that directory before the agent starts, so they are portable across runtimes.

Skills bundled with the application

The default way to ship a skill, because it travels with the build that was tested with it. Put it on the classpath:

src/main/resources/
└── skills/
    └── release-checks/
        ├── SKILL.md
        └── scripts/
            └── check_versions.sh
application.yaml
spring:
  acp:
    skills:
      - path: skills/release-checks          # classpath directory; installed as "release-checks"

This works from an IDE (target/classes) and from an executable jar. Scripts that start with a shebang are marked executable when copied out of a jar.

Skills from a Git repository

spring:
  acp:
    skills:
      - url: https://github.com/acme/agent-skills
        path: plugins/mailgun/skills/mailgun        # directory inside the repository
        ref: 8ae7aaf85bd1283dedb449d7fdb2192e05e27b5a  # full commit pins it; a branch or tag also works
        sha256: 3f9c…                               # optional: expected SHA-256 of SKILL.md

      - url: https://github.com/acme/private-skills
        path: review-rubric
        token: ${GITHUB_TOKEN}                      # for a private repository
  • Fetched with the system git, so git must be on the PATH. HTTPS only.
  • Without ref, the default branch is used, and the startup log names the commit to pin it to. A 40-character commit is checked against what Git actually resolved.
  • A token reaches only that one git process, as an environment-borne header: never in a URL, an argument, a file or a log line.

How installation behaves

  • Before first use. Skills are installed when the first agent connection opens, once per JVM for a given workspace and skill list.
  • Fails closed. A skill that cannot be fetched, has no SKILL.md, contains a symbolic link, or fails its digest or pin check stops the agent from starting, rather than letting it start without a capability you rely on.
  • Reconciled. Each installed skill carries a .spring-ai-acp-skill marker. A skill removed from configuration is removed from the workspace at the next start.
  • Your own skills are safe. A directory under .agents/skills/ without the marker is never overwritten or removed; a configured skill with the same name fails instead. You can still author skills by hand directly in <workspace>/.agents/skills/ without configuring them.

Writing a skill

skills/release-checks/SKILL.md
---
name: release-checks
description: Verify a release candidate before it is tagged. Use when asked to check,
  validate or sign off a release, RC or version bump.
---

# Release checks

1. Confirm the version in `pom.xml` has no `-SNAPSHOT` suffix.
2. Confirm `CHANGELOG.md` has an entry for this version.
3. Run `scripts/check_versions.sh` and report any dependency whose version changed.

Report each step as PASS or FAIL with one line of evidence. Do not tag anything.

The description is what the agent matches a task against, so write it as when to use this. Name the skill in the prompt ("…using the release-checks skill") when you need deterministic behaviour.

Warning

A skill that runs scripts needs the agent to have a shell tool, and runs that script with the agent's environment, which it inherits from your JVM. Goose needs its developer builtin (spring.acp.runtimes.goose.builtins: developer) unless its own config already enables it. A secret the script reads (say MAILGUN_API_KEY) must be in your application's environment. The spring.acp.terminal settings do not govern the agent's own shell.

Tip

If the workspace lives in your source tree, add workspace/.agents/ to .gitignore: it is rebuilt from configuration on every start.

Agent Instructions (AGENTS.md)

AGENTS.md is a Markdown file of standing instructions: who the agent is serving, what the project is, its conventions, what it must never do. It is effectively the agent's system prompt. Unlike a skill, which loads on demand, AGENTS.md is in context on every turn.

Agents read it from their working directory. Spring AI ACP does not push instructions over the protocol; it sets the working directory with spring.acp.workspace. So installing instructions means putting AGENTS.md at the workspace root. Goose, Codex and OpenCode all read it there.

workspace/                      ← spring.acp.workspace
├── AGENTS.md                   ← always in context
└── .agents/
    └── skills/                 ← installed by Spring AI ACP; loaded on demand
        └── release-checks/
            └── SKILL.md

Writing AGENTS.md

workspace/AGENTS.md
# Orders service assistant

You help the order-management team investigate failed orders. The people you talk to
run operations, not infrastructure: lead with business impact and keep jargon out.

## Tools

- `orders__getOrder`, `orders__listFailures`: read-only, call freely.
- `orders__refund`: moves money. Present the refund and wait for an explicit "yes".

## Conventions

- Cite order ids in every answer.
- Never guess a customer's details; look them up or say you cannot.

Keep it short and about things that apply to every turn. It is paid for on every turn and competes for attention with everything else in context. Anything that starts "when asked to…" belongs in a skill.

Installing it

Option 1: a workspace directory in your project

The simplest approach, used by acp-meridian: keep a workspace/ directory in the repository with AGENTS.md in it, and point at it.

spring:
  acp:
    workspace: ${WORKSPACE_DIR:./workspace}

The relative path is resolved against the JVM's working directory, so run the application from the project root, or set WORKSPACE_DIR to an absolute path in deployment.

Option 2: ship it in the jar and stage it at startup

When the application runs from a jar with a workspace it does not own (a container volume, a temp directory), package AGENTS.md as a resource and copy it into place. The agent is launched on the first prompt, so a component that runs during context startup is always in time:

src/main/java/com/example/orders/agent/InstructionsInstaller.java
@Component
class InstructionsInstaller {

    /** Copies classpath:agent/AGENTS.md to the workspace root before the agent is launched. */
    InstructionsInstaller(AgentSettings settings,
            @Value("classpath:agent/AGENTS.md") Resource instructions) throws IOException {
        try (InputStream in = instructions.getInputStream()) {
            Files.copy(in, settings.workspace().resolve("AGENTS.md"), StandardCopyOption.REPLACE_EXISTING);
        }
    }
}

AgentSettings is the auto-configured bean carrying the resolved, absolute workspace. The same component is the natural place to render the file from a template if it must vary per deployment.

Permissions and the Workspace

Permission policy

When an agent asks permission to run a tool (session/request_permission), Spring AI ACP answers on your behalf, since a server-side application has no human at the keyboard. Every request gets an answer, so no turn stalls. The exception is ask, for an application someone is sitting at.

spring:
  acp:
    permissions:
      policy: allowlist          # deny (default) | allowlist | auto-approve | ask
      allowed-tools:
        - developer__text_editor
        - inventory__lookup_part
PolicyBehaviour
denyRejects everything. The agent degrades to answering from context.
allowlistApproves exactly the named tools (case-insensitive) and rejects the rest, including any request whose tool name cannot be determined.
auto-approveApproves everything. Only in a sandbox, or when the gate that matters is elsewhere (see acp-meridian's AGENTS.md).
askPuts each request to a person through the application's PermissionPrompt bean. spring-ai-acp-console provides one (see the console); without one, the application fails to start rather than guess.

To find the names an agent reports, run once with logging.level.org.springaicommunity.acp: DEBUG and read them off the permission requests.

Mode decides whether the question is asked

Warning

policy: deny alone does not stop an agent writing files. In their default modes, Goose, Codex and OpenCode all edit files with their own tools without asking at all. The mode decides whether permission is requested; the policy decides the answer. For a read-only reviewer, set both:

spring:
  acp:
    mode: plan            # goose: approve
    permissions:
      policy: deny

Codex's read-only mode still writes inside the workspace without asking; use plan.

Lending the client's filesystem and terminal

ACP lets an agent borrow the client's file and terminal access. A server-side application rarely needs either, so both are off, and are declared unsupported to the agent:

spring:
  acp:
    filesystem:
      enabled: false        # answer fs/read_text_file
      write: false          # also answer fs/write_text_file (implies enabled)
    terminal:
      enabled: false        # answer terminal/*: arbitrary execution as this JVM's user
      allowed-commands: []  # empty allows any; matched by file name
      output-limit: 1MB
      command-timeout: 5m
      max-concurrent: 8

When enabled, every path is confined to the workspace by its real path, with symlinks followed, so neither .. nor a planted symlink escapes. This governs only what the agent asks this client to do. Its own process's file access is the operating system's to restrict: run the agent as a user, or in a container, that can reach only what it should.

Where adapters write

Adapters write agent config files (config.toml, opencode.json) to spring.acp.runtime-home, never to the workspace. It defaults to a directory under the JVM's temp directory named for the runtime. The only thing Spring AI ACP writes into the workspace is .agents/skills/.

Spring AI ChatModel

Add spring-ai-acp-ai and an AcpChatModel bean appears wherever a Spring AI application looks for a ChatModel:

ChatClient chat = ChatClient.create(chatModel);

String answer = chat.prompt()
        .user("Review the pending changes")
        .options(AcpChatOptions.builder().session("review-123").mode("plan").build())
        .call()
        .content();
  • No session (the default): each call is a throwaway ACP session, and the whole message list is sent. Use this with Spring AI's ChatMemory.
  • A named session: the agent already holds the conversation, so only messages after the last assistant message are sent. Don't combine it with a ChatMemory advisor.
  • temperature, topP, maxTokens and similar have no ACP equivalent; they are logged once and ignored. Spring AI ToolCallbacks are not visible to the agent; give it tools as MCP servers.
  • Disable with spring.acp.chat-model.enabled=false.

Terminal Console

spring-ai-acp-console turns the application into a terminal chat with its agent. It is for the stage where you are designing the agent itself — its AGENTS.md, its skills, its MCP servers — and want to talk to it before there is any other front end. Add the dependency and run the application; there is no code to write.

<dependency>
    <groupId>org.springaicommunity</groupId>
    <artifactId>spring-ai-acp-console</artifactId>
    <version>${spring-ai-acp.version}</version>
</dependency>

It opens the session before the first prompt, so the model the negotiated tier actually applied is on screen before any tokens are spent, along with anything the agent reported outside the protocol, such as an MCP server it could not load. Each turn is streamed: assistant text as it arrives, a dimmed line per tool call, thought and plan update, a line for any tool call that fails, and the agent's context usage when the turn ends.

When it runs

The module is safe to leave on the classpath of an application that is also tested and deployed, because by default the console only starts when the process is attached to an interactive terminal. Nothing is registered otherwise: no bean, no terminal, and nothing reading stdin.

spring.acp.console.enabledBehaviour
unset (default)Runs when stdin and stdout are a terminal: java -jar or mvn spring-boot:run from a shell. A test, a CI job or a deployed service is left alone.
trueAlways runs, reading plain lines when there is no terminal. For driving it from a pipe or a script.
falseNever runs.

The console starts on its own thread once the application is ready, so startup completes normally and a web application keeps serving while it runs. When the user leaves, the console closes the application context, which stops the agent and ends the process. In a web application that stops the server too.

Answering permission requests

With policy: ask, the console puts each of the agent's permission requests to you, part-way through the turn, as a numbered choice between the options the agent offered:

spring:
  acp:
    mode: plan              # so the agent asks before it acts (see "Mode decides whether the question is asked")
    permissions:
      policy: ask
  ? The agent wants to: Run `./send-report.sh`  (execute · developer__shell)
    1) Allow once
    2) Always allow
    3) Reject
  choose 1-3 (Ctrl-C to cancel) › 3

Ctrl-C at that prompt cancels the request, which the agent hears as a cancellation rather than a refusal. This is the most direct way to see what an agent is about to do while designing it. It is also a prompt per tool call, so an agent whose job is calling tools may be better served by allowlist and a gate in its instructions, as acp-meridian does.

Note

Time spent answering counts against the turn's spring.acp.timeout. The prompt applies to every session in the application, not only the console's, so an application that also serves web users should leave ask to the console-only profile it runs locally.

Customizing

  • How turns look: register a subclass of ConsoleRenderer as a bean. Every method is an override point, and render(AgentEvent) is the one each event goes through.
  • Who answers ask: register your own PermissionPrompt bean, and the console's backs off. PermissionQuestion carries the tool name, the agent's title for the call, its kind and the options.
  • The terminal: a JLine Terminal bean replaces the system one.
Tip

Log lines are written to the same terminal and land in the middle of the conversation. A console application usually wants logging.level.root: WARN and a bare pattern such as logging.pattern.console: "%msg%n", as acp-meridian uses.

Observability

With Micrometer on the classpath, every turn and every tool call is an observation: a timer, and a span parented to whatever the caller was in.

acp.turn{acp.runtime=goose, acp.model=gpt-5.6-terra, acp.session.kind=named, acp.outcome=END_TURN}
acp.tool.call{acp.runtime=goose, acp.tool.kind=READ, acp.tool.status=COMPLETED}

acp.model is the model the session is really using, not the one requested. Session names, tool titles and usage are span attributes, not meter tags; contribute an ObservationConvention to change that. Disable with spring.acp.observations.enabled=false.

Testing

Testing your application

Switch the auto-configuration off and mock the client. No agent process, no provider key:

@SpringBootTest(properties = "spring.acp.enabled=false")
class ReviewControllerTests {

    @MockitoBean
    AgentClient agent;

    @Test
    void summarizes() {
        AgentClient.PromptSpec spec = mock(AgentClient.PromptSpec.class, RETURNS_SELF);
        AgentClient.AgentResponse response = mock(AgentClient.AgentResponse.class);
        given(agent.prompt()).willReturn(spec);
        given(agent.prompt(anyString())).willReturn(spec);   // prompt(text) is a default method
        given(spec.call()).willReturn(response);
        given(response.content()).willReturn("Looks good");
        // …
    }
}

For a test against a real agent, gate it on the agent being usable so CI without one stays green, and pin the model so a developer's local agent config cannot change the outcome.

Testing a runtime adapter

spring-ai-acp-test is for adapter authors. AgentRuntimeContract is the conformance suite every compiled adapter extends; it asserts only what ACP standardizes. ScriptedAgent is a fake agent speaking raw JSON-RPC over an in-memory transport, and AgentProbe skips live suites when an agent is absent or has no credentials. Live suites cost real tokens, so they only run with -Dspring-ai-acp.test.live=true.
